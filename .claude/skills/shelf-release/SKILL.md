# Shelf Release Workflow

Цей skill випускає нову версію Shelf - відповідник процедури з [RELEASE.md](RELEASE.md), але з автоматизацією рутини і чотирма гейтами підтвердження, щоб не натиснути «реліз» випадково.

## Що робить (огляд)

1. Аналізує коміти від попереднього тега, рекомендує SemVer-бамп.
2. **Гейт 1**: користувач обирає номер версії.
3. Генерує чернетку CHANGELOG-секції з комітів, переклад на укр.
4. **Гейт 2**: користувач редагує/затверджує текст.
5. Правит `Shelf.csproj` і `CHANGELOG.md`, показує `git diff`.
6. Виводить smoke-test чек-лист із RELEASE.md.
7. **Гейт 3**: користувач підтверджує що smoke test пройшов.
8. Комітить «Release vX.Y.Z» на main + push.
9. **Гейт 4**: фінальний «пушити тег?» (точка неповернення).
10. `git tag -a vX.Y.Z -m "..."` + `git push origin vX.Y.Z` → release.yml в хмарі підхоплює.
11. Звіт з URL Actions і майбутньої сторінки Releases.

## Преконтролі (виконати ДО будь-яких дій)

1. **Правильний проект**: cwd має містити `Shelf.sln` і `Shelf.csproj`. Path-agnostic.

   ```bash
   if [ ! -f Shelf.sln ] || [ ! -f Shelf.csproj ]; then
     echo "Not a Shelf project (Shelf.sln/Shelf.csproj missing in $(pwd))"
     exit 1
   fi
   ```

2. **Робоча тека чиста**. Якщо `git status --short` показує будь-що — **СТОП**. Реліз-коміт повинен містити **тільки** Shelf.csproj + CHANGELOG.md, не нічого більше.
   - Пропонуй варіанти: (а) спочатку зробити `shelf-commit` для існуючих змін, (б) `git stash` їх на час релізу, (в) `git checkout -- <файли>` якщо це сміття.
   - Без явного дозволу користувача — не йди далі.

3. **Гілка `main`**:
   ```bash
   git branch --show-current
   ```
   Якщо не на `main` — попередь і запропонуй `git checkout main`. Реліз з feature-гілок проектом не передбачено.

4. **Локальний main = origin/main**:
   ```bash
   git fetch origin && git status -uno
   ```
   Якщо позаду — запропонуй `git pull --ff-only`. Без апдейта не релізимо.

5. **Останній тег**:
   ```bash
   LAST_TAG=$(git describe --tags --abbrev=0 2>/dev/null || echo "")
   ```
   Якщо порожньо — це самий перший реліз. Запропонуй `v1.0.0` за замовчуванням.

6. **Поточна версія в csproj** (для звіряння):
   ```bash
   grep "<Version>" Shelf.csproj | head -1
   ```

## Етапи виконання

### Етап 1: Аналіз комітів

```bash
git log "${LAST_TAG}..HEAD" --oneline --no-merges
```

Парс кожного рядка регулярним виразом `^[0-9a-f]+\s+(feat|fix|docs|style|refactor|perf|test|chore|ci|build)(\([^)]+\))?:\s*(.*)$`:

- Збираєш у словник `{type: [list of subjects]}`.
- Рахуєш N штук кожного типу.

**Правила рекомендації версії:**

| Виявлено в комітах | Рекомендація |
|---|---|
| Хоча б один з body містить `BREAKING CHANGE:` | **MAJOR** (1.x → 2.0.0) |
| Хоча б один `feat:` | **MINOR** (1.0 → 1.1.0) |
| Тільки `fix:`, `perf:`, `chore:`, `docs:`, `ci:`, `style:`, `refactor:`, `test:`, `build:` | **PATCH** (1.0.0 → 1.0.1) |
| Жодних розпізнаних — лише довільні коміти | **PATCH** (за замовчуванням, попередити користувача) |

Покажи користувачу:
- Останній тег (`v1.0.1`)
- Скільки комітів пройшло (`N комітів від v1.0.1`)
- Розбивку за типами (`1 feat, 2 fix, 1 chore, 1 docs`)
- Свою рекомендацію з обґрунтуванням

### Гейт 1: Версія

Запитай користувача (через AskUserQuestion або просто текстом):

> «Поточна версія: **1.0.1**. Рекомендую **1.1.0** (бамп MINOR — є нова фіча). Яку версію ставимо?»

Можливі відповіді:
- Точна цифра типу `1.1.0`, `1.0.2`, `2.0.0` — використовуй.
- «Як рекомендуєш» / «погоджуюсь» — бери рекомендовану.
- «Інше» / «давай patch» / «major» — переходь до тієї логіки.

**Валідація:**
- Формат `^\d+\.\d+\.\d+$` (рівно три числа через крапку).
- Монотонно більша за `LAST_TAG`. Помилка: «Версія X.Y.Z не більша за поточну A.B.C. Реліз скасовано».
- Тег `vX.Y.Z` ще не існує (`git tag --list v$VERSION` має бути порожнім; `git ls-remote --tags origin v$VERSION` теж).

### Етап 2: Чернетка CHANGELOG-секції

З розбивки за типами сформуй розділи в форматі «Keep a Changelog»:

| Conventional prefix | CHANGELOG розділ |
|---|---|
| `feat` | **Додано** |
| `fix` | **Виправлено** |
| `refactor`, `style`, `perf` | **Змінено** |
| `docs` | **Документація** |
| `chore`, `ci`, `build`, `test` | (не показуємо в CHANGELOG — це інфраструктура, користувачу нерелевантно) |

Для кожного commit subject:
- Прибери префікс і `(scope):` якщо є.
- Якщо subject англійською — спробуй короткий ручний переклад на укр (типова термінологія: «add» → «додано», «fix» → «виправлено», «remove» → «видалено», «update» → «оновлено», «refactor» → «реструктуризовано»). Якщо не впевнений — лиш як є.
- Кожен пункт оформ як `- <текст>.`

Приклад згенерованої секції:

```markdown
## [1.1.0] - 2026-05-27

### Додано
- Віджет NBA: результати плейофф, розклад майбутніх ігор, налаштування улюблених команд і вікно деталей із поквартальним рахунком.

### Виправлено
- Заміна системного синього фокус-бордера TextBox на тематичний сірий через глобальний стиль у Theme.xaml.
```

### Гейт 2: CHANGELOG

Покажи користувачу чернетку повністю. Запропонуй:
- «Підходить — записуй» → продовжуй.
- «Зміни N-й пункт на ...» / «додай рядок ...» / «прибери ...» → редагуй і покажи знову.
- «Перепиши з нуля» → попроси користувача надати весь текст.

Не йди далі без явного «так / OK / запиши».

### Етап 3: Правки файлів

**Shelf.csproj** — заміни три рядки:

```xml
<Version>X.Y.Z</Version>
<FileVersion>X.Y.Z.0</FileVersion>
<AssemblyVersion>X.Y.Z.0</AssemblyVersion>
```

Використовуй Edit tool з точним old_string. Якщо існуючий формат відрізняється (наприклад, без `.0` у FileVersion) — підлаштуйся, але приведи до канонічного.

**CHANGELOG.md** — структура така:

```markdown
## [Unreleased]

### Заплановано
- (TODO-пункти, не чіпай)

---

## [X.Y.Z] - YYYY-MM-DD   ← ВСТАВ СЮДИ нову секцію

### Додано
- ...

### Виправлено
- ...

---

## [1.0.1] - 2026-05-27
... (попередня версія, не чіпай)
```

**Critically**: новий блок вставляється МІЖ `[Unreleased]` і попередньою версією, не замість `[Unreleased]`. Це збереже список TODO-пунктів, які лишаються заплановані.

Також онови comparison-links внизу файлу:

```markdown
[Unreleased]: https://github.com/bridges-net-ua/shelf/compare/v{NEW}...HEAD
[{NEW}]: https://github.com/bridges-net-ua/shelf/compare/v{LAST}...v{NEW}
[{LAST}]: https://github.com/bridges-net-ua/shelf/compare/v{PREV-LAST}...v{LAST}
... (existing entries)
```

Дата `YYYY-MM-DD` — поточна (`date +%Y-%m-%d`).

Після правок виконай:
```bash
git diff Shelf.csproj CHANGELOG.md
```

Покажи diff користувачу. Це інформативний крок без явного гейту — наступний гейт відразу.

### Гейт 3: Smoke test

Виведи користувачу чек-лист (адаптуй із RELEASE.md розділ «Локальний smoke test»):

```
🧪 SMOKE TEST (зроби руками перед коміт-релізом):

cd "d:\project\Shelf"
Get-Process -Name Shelf -ErrorAction SilentlyContinue | Stop-Process
dotnet build Shelf.sln -c Release
Start-Process bin\Release\net8.0-windows\Shelf.exe

Перевір:
✓ Додавання різних віджетів + перезапуск (стан зберігся)
✓ Перемикання теми Dark ↔ Light (без рестарту)
✓ Перемикання мови Uk ↔ En (потребує рестарту)
✓ Holidays: редагування зі всіма полями (Year/Emoji/Note)
✓ Holidays: експорт/імпорт JSON, експорт/імпорт TXT
✓ Photos: обрання папки, зміна фото
✓ Radio: відтворення, гучність
✓ Weather: кеш одразу при старті
✓ Timer: завершення + алярм
✓ Stopwatch: Start → Lap → Pause → Reset
✓ NBA (якщо є): tooltip серії, логотипи, дата майбутніх жирним

Скажи «зробив(ла)» коли пройдеш, або «провалився <деталь>» якщо знайшов баг.
```

**Не комітимо без відповіді.** Якщо користувач каже «провалився» — зупиняй реліз, не комітимо нічого, не пушимо. Користувач спершу через `shelf-update` фіксує, потім перезапускає `shelf-release`.

### Етап 4: Реліз-коміт

Якщо користувач сказав «зробив(ла)» — продовжуй:

```bash
git add Shelf.csproj CHANGELOG.md
git commit -m "$(cat <<'EOF'
Release v{X.Y.Z}

(Опційно: 1-2 рядкові highlights, або порожньо)

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"
git push origin main
```

Якщо `git push` провалюється (rejected non-fast-forward — хтось запушив у main між тим) — **СТОП**. Не пробуй `--force`. Скажи користувачу: «Локальний main позаду origin після нашого fetch. Зроби `git pull --ff-only` і запусти `shelf-release` знову — або скажи `--force` явно, якщо точно хочеш переписати».

Дочекайся щоб push пройшов. Покажи commit SHA.

### Гейт 4: Push тега (фінальний)

Покажи планові команди:

```bash
git tag -a v{X.Y.Z} -m "Release v{X.Y.Z}"
git push origin v{X.Y.Z}
```

Скажи користувачу:

> «Все готово до фінального кроку. Це **точка неповернення** — після push'у тега workflow в хмарі автоматично побудує `.exe` і опублікує на сторінці Releases. Скасувати = видалити тег з GitHub і Releases вручну. Пушимо?»

Чекай явне «так / OK / пушим». «Ні» / «зачекай» / мовчання = СТОП без жодних дій.

### Етап 5: Tag + push

```bash
git tag -a v{X.Y.Z} -m "Release v{X.Y.Z}"
git push origin v{X.Y.Z}
```

### Етап 6: Звіт

```
✅ Реліз v{X.Y.Z} запущено.

Коміт:           {SHA} "Release v{X.Y.Z}"
Тег:             v{X.Y.Z} (annotated)
Запущено гілку:  main

🔗 GitHub Actions:    https://github.com/bridges-net-ua/shelf/actions
🔗 Майбутній Release: https://github.com/bridges-net-ua/shelf/releases/tag/v{X.Y.Z}

Workflow `release.yml`:
1. dotnet publish self-contained win-x64 (~3-5 хв)
2. Створює `Shelf-v{X.Y.Z}-win-x64.zip` (~70 МБ)
3. Публікує GitHub Release з auto-generated notes + zip attachment

Подивись Actions для прогресу. Коли стане ✅ — реліз готовий до скачування.

Після релізу (з RELEASE.md):
- Перевір, що zip прикріпився і завантажується
- Завантаж на чисту машину, розпакуй, запусти
- Закрий issues з міткою `fixed-in-next-release`
```

## Чого НЕ робити

- ❌ **`dotnet publish` локально** — заборонено глобальним правилом користувача (тільки після `ЗІБРАТИ EXE`). Збірка для релізу робиться в хмарі через release.yml. Skill не запускає `publish` навіть «щоб перевірити».
- ❌ **`git push --force`, `--force-with-lease`** — заборонено без явного дозволу (глобальне правило).
- ❌ **`git tag -d` або `git push origin :v{X.Y.Z}`** — не видаляй теги. Якщо потрібно — користувач робить вручну.
- ❌ **`git commit --amend` після `git push`** — переписує опубліковану історію.
- ❌ **`--no-verify`** — не пропускати hooks.
- ❌ **Створювати feature-бранчі** — реліз з `main`, без gitflow.
- ❌ **Бампити версію без `Release vX.Y.Z` коміту** — щоб історія мала чіткий «реліз-маркер».
- ❌ **Релізити з брудної теки** — щоб у `Release vX.Y.Z` коміт не потрапили чужі правки.
- ❌ **Скакати через гейти** — кожен гейт обов'язковий, навіть якщо здається «очевидно».
- ❌ **Самому редагувати GitHub Release notes через `gh release edit`** — `generate_release_notes: true` у workflow робить це автоматично, не заважаємо.

## Особливі випадки

### Hotfix-реліз (1.0.1 → 1.0.2)

RELEASE.md описує hotfix з окремою гілкою від тегу. Skill це не автоматизує — для hotfix:
- Користувач сам створює гілку `git checkout -b hotfix/1.0.2 v1.0.1`.
- Робить фікс через `shelf-update` і `shelf-commit`.
- Мерджить у main (`git checkout main && git merge hotfix/1.0.2`).
- Запускає `shelf-release` — обирає `1.0.2` як PATCH.

Якщо користувач каже «хочу hotfix» прямо — поясни цей флоу і запитай чи готові його провести вручну.

### Перший реліз (нема попередніх тегів)

Якщо `git describe --tags` повертає помилку — це перший реліз. Дефолтна рекомендація `1.0.0`. Range комітів для аналізу = всі коміти на main.

### Користувач хоче кастомну версію (1.2.0-rc1)

Skill не підтримує pre-release-теги в форматі `vX.Y.Z-suffix` — release.yml workflow ловить тільки `v*.*.*` без суфіксів (трикрапкова перевірка `^v\d+\.\d+\.\d+`). Якщо користувач просить — поясни обмеження.

### Користувач хоче змінити CHANGELOG ПІСЛЯ релізу

Це нормально — CHANGELOG.md можна редагувати в звичайному коміті після релізу, GitHub Releases не торкаємо.

### Скасування на гейті

На будь-якому гейті користувач каже «ні / стоп / скасувати» → СТОП. Якщо вже були правки `Shelf.csproj` і `CHANGELOG.md` (між Етап 3 і Гейт 3) — запропонуй `git restore Shelf.csproj CHANGELOG.md` щоб відкотити. Без коміта/тега ці правки локальні, легко відкатуються.

### `gh` CLI відсутній

Skill не використовує `gh` напряму — все через нативний `git`. Тому `gh` не обов'язковий.

### Версія в `Shelf.csproj` уже відповідає планованому релізу

Якщо `Shelf.csproj` уже на `1.1.0` (наприклад, користувач бампив вручну), а тега `v1.1.0` нема:
- Перевір, що CHANGELOG також уже має секцію `[1.1.0]`.
- Якщо так — пропусти Етап 1-3, переходь одразу до Гейт 3 (smoke test) + Гейт 4 (tag).
- Якщо ні — продовжуй штатно з Етапу 2 (без правки `Shelf.csproj`, лише CHANGELOG).
